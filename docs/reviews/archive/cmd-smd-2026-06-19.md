# cmd/smd code review - 2026-06-19

Scope: `cmd/smd`, including daemon startup/shutdown, `smd import`, and the
adjacent contracts this composition root wires together: config loading,
HTTP serving, forwarder workers, enrichment, bridge, FT8 logging/TX, PSK
Reporter, SQLite, and user-facing documentation.

Review posture: approached as a fresh package review. I read the command source,
tests, closest boundary packages, and the current docs that describe how
operators run `smd` and `smd import`.

Focus areas: correctness, performance, security, test coverage, and
documentation.

## Findings

### H1 - Unix socket startup can delete a non-socket file named by `socket_path`

`cmd/smd` passes the loaded `cfg.SocketPath` directly into
`server.ListenAndServe` (`cmd/smd/main.go:631-635`). When
`server.protocol == "unix"`, the API server unconditionally removes that path
before binding (`internal/api/server.go:291-303`), and shutdown also removes the
cached path (`internal/api/server.go:354-360`).

That stale-socket cleanup does not check that the existing path is actually a
socket. If an operator typo points `socket_path` at a regular file that the
daemon user can delete, startup unlinks it before `net.Listen("unix", ...)`
creates the socket. This is especially sharp because the same config file can
also hold local secrets; a typo such as a Unix `socket_path` aimed at
`config.json`, an export, or another user-writable file becomes destructive.

The config validator does not close this gap. `Validate` does not include server
path validation (`internal/config/validate.go:57-80`), and the only socket-path
advisory is for non-loopback TCP binds (`internal/config/config.go:989-998`).

Recommendation: for Unix listeners, `lstat` first. Remove only when the existing
path is a Unix socket; if it exists as any other file type, fail startup with a
clear config error. Add a regression test that creates a regular file at the
configured socket path and asserts it is not removed.

### M1 - Server tunables bypass config validation and can panic or disable guards

`ServerConfig` controls the daemon listener, HTTP timeouts, body cap, paging
limits, concurrent-request cap, SSE cap, submit rate limiter, and profiling
toggle (`internal/config/config.go:409-485`). `applyDefaults` only fills zero
values; it does not reject negative or nonsensical non-zero values
(`internal/config/config.go:738-808`). `Validate` omits the server block
entirely except for the non-loopback TCP warning (`internal/config/validate.go:57-80`).

That lets malformed hand-edited config reach runtime. A negative
`server.max_concurrent_requests` panics in `newLoadLimiter` when it creates the
semaphore channel (`internal/api/limits.go:45-48`), so a bad config produces the
top-level panic path rather than a normal "invalid config" startup error. Other
bad values degrade safety more quietly: non-positive HTTP timeout durations are
treated by `net/http` as disabled, undermining the slow-header guard; a negative
or zero submit bucket can effectively block submits; invalid paging/body caps
also reach handlers (`internal/api/body.go:23-31`).

Recommendation: add a `validateServer` pass under `config.Validate` with an enum
check for `protocol`, positive bounded values for all HTTP timeouts and resource
caps, `default_page_limit <= max_page_limit`, sane body-size and contact-history
ceilings, and `enable_profiling` warnings when combined with a non-loopback TCP
bind. Pin this with config-load tests for negative limits and runtime tests that
no invalid config reaches `api.New`.

### M2 - Completed FT8 QSO log jobs are not drained during shutdown

The completed-QSO sink intentionally leaves the FT8 decode loop by launching a
one-shot goroutine with `safego.Go` (`cmd/smd/main.go:478-550`). That goroutine
can do enrichment, write a QSO through `qsoSvc.Submit`, publish to the daemon
event hub, and publish an `ft8-logged` event. `safego.Go` is explicitly
untracked (`internal/safego/safego.go:83-88`), unlike `GoTracked`.

Shutdown cancels `workerCtx`, stops bridge/FT8/PSK Reporter, shuts down HTTP,
waits only for `workerWG`, then closes the daemon hub
(`cmd/smd/main.go:660-735`). The comment says all publishers have stopped by
then (`cmd/smd/main.go:725-727`), but the FT8 QSO logger is not represented in
that accounting. A completed exchange that just handed off to this goroutine can
race shutdown: it may see the canceled context and fail to store an already
completed on-air QSO, or it may still be unwinding while DB/logger teardown is
approaching. The FT8 service itself only waits for capture/decode/TX goroutines,
not for this command-level logger callback (`internal/ft8/service.go:167-178`).

Recommendation: make FT8 QSO logging a tracked lifecycle participant in
`cmd/smd`, for example a small `qsoLogWG` plus a bounded drain in the same
shutdown timeout window. If shutdown should intentionally drop in-flight
completed-QSO logs, document that as an explicit best-effort policy and add a
regression test that covers the chosen behavior.

### L1 - CLI help still advertises the removed `./config.json` fallback

Both daemon and import flag help still say the default config path is
`$SM_WORKING_DIR/config.json or ./config.json` (`cmd/smd/main.go:135`,
`cmd/smd/import.go:55`). Current code removed the cwd fallback: `defaultConfigPath`
uses `utils.WorkingDir`, which resolves `SM_WORKING_DIR`, then XDG data dir for
system-path installs, then the executable directory for portable/dev use
(`cmd/smd/main.go:1056-1085`). The operator docs now describe the XDG fallback
correctly (`docs/install.md:195-198`, `docs/install.md:231-236`), so the drift is
confined to runtime help text.

Recommendation: update both flag descriptions to match the real resolver and add
a small assertion around the help/usage string or at least a package comment note
so the old cwd fallback does not reappear in user-facing text.

## Coverage Notes

The strongest existing coverage is around the known historical risks:

- Config path resolution and first-run seeding are covered, including no cwd
  fallback and resolver failure propagation (`cmd/smd/main_test.go:329-460`,
  `cmd/smd/main_test.go:694-710`).
- Default-logbook self-heal covers missing rows, setup-incomplete behavior,
  invalid IDs, and persist-failure in-memory correction.
- Forwarder worker spawning covers disabled entries, unknown types, missing
  default retry, explicit retry overrides, invalid worker config, and goroutine
  drain.
- Import covers happy path, dry-run, idempotency, historical `MY_*` preservation,
  mode normalization, and QRZ LOGID stamping (`cmd/smd/import_test.go:170-319`).
- Adjacent packages cover listener shutdown, SSE stream shutdown, bridge TX
  readiness, FT8 service lifecycle, PSK Reporter late-shutdown flush, and lookup
  context propagation.

Missing coverage directly tied to the findings:

- Unix socket cleanup should test "regular file at socket_path is not removed".
- Server config validation needs negative/oversized values for every `ServerConfig`
  knob, plus a test proving invalid configs fail before `api.New`.
- FT8 completed-QSO logging needs a shutdown/drain test around the command-level
  callback or an explicit documented drop policy.
- CLI usage text should be checked against the current resolver behavior.

## Resolution (2026-06-19)

All four findings fixed. Operator decision: M2 → track + drain (guarantee the
log), not best-effort drop.

- **H1 (fixed — destructive socket cleanup).** `ListenAndServe`'s Unix
  pre-bind cleanup now `lstat`s the path first and removes it only when it's
  actually a socket; a path that exists as any other file type (a typo'd
  `socket_path` aimed at `config.json`, an export, another user file) makes
  startup fail with a clear config error instead of unlinking the file. Test:
  `api.TestListenAndServe_UnixRefusesNonSocketPath` (a regular file at the path
  is left intact and startup errors).
- **M1 (fixed — server tunables bypassed validation).** New `validateServer`
  pass in `config.Validate`: `protocol ∈ {tcp,unix}`; all HTTP timeouts, body
  cap, paging limits, contact-history cap, concurrency/SSE caps, and the submit
  bucket must be positive; `default_page_limit ≤ max_page_limit`; and an advisory
  warning for `enable_profiling` on a non-loopback TCP bind. `applyDefaults` only
  fills zeros, so a hand-edited negative previously reached runtime — a negative
  `max_concurrent_requests` panicked `newLoadLimiter`, non-positive timeouts
  silently disabled the slow-header guard. These are now config errors caught
  before `api.New` (fatal at Load / 400 at PUT). Deliberately no arbitrary upper
  ceilings — a large-but-valid operator value isn't a safety hazard and capping
  it would reject legitimate tuning. Tests: `config.TestValidateServer_*`
  (defaults clean, nonsense values rejected, page-limit ordering, profiling
  advisory).
- **M2 (fixed — FT8 completed-QSO logs not drained at shutdown).** The
  completed-QSO sink now launches its off-pipeline log+enrich via a new
  `launchFt8QsoLog` helper: `safego.GoTracked` registers it on a new `qsoLogWG`
  synchronously on the decode loop (which `ft8Svc.Stop()` drains, so every
  in-flight job is accounted for before shutdown proceeds), and the work runs
  under a fresh `context.Background()`-derived context bounded by
  `ft8QsoLogTimeout` (30s) instead of the decode-loop context that `Stop` cancels
  — so a QSO that already completed on the air is still persisted during the
  drain rather than aborting on a cancelled context. Shutdown drains `qsoLogWG`
  within the existing shutdown-timeout window, after `ft8Svc.Stop()` and before
  the daemon hub / DB tear down. (`PublishQsoLogged` to the already-closed FT8 hub
  is a safe no-op; the QSO still reaches the DB via `qsoSvc.Submit`.) Tests:
  `TestLaunchFt8QsoLog_TrackedAndDrains`,
  `TestLaunchFt8QsoLog_ContextDecoupledFromDecodeLoop`.
- **L1 (fixed — stale CLI help).** Both the daemon and `import` `-config` flag
  descriptions now match the real resolver (`$SM_WORKING_DIR`, else the XDG data
  dir for a system install, else the executable's directory); the removed
  `./config.json` cwd fallback is gone from user-facing text.

Verified: `gofmt`/`go vet` clean; `cmd/smd`, `internal/config`, `internal/api`
build + pass; `-race` clean on `cmd/smd`, `internal/config`, `internal/api`;
`CGO_ENABLED=0 go build ./...` succeeds.
