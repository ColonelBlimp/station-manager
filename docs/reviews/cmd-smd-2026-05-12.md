# `cmd/smd` — focused code review (2026-05-12)

## Scope

Narrow re-review of the daemon entry point only:

- `cmd/smd/main.go`
- `cmd/smd/doc.go`
- `cmd/smd/main_test.go`

Dependency surfaces were spot-verified (signatures and lifecycle
semantics) where `cmd/smd` relies on a contract, but the depended-on
packages themselves are out of scope. The broader daemon review at
`docs/reviews/cmd-smd-and-imports.md` (2026-05-07) remains the
authoritative cross-package pass.

This review revisits `cmd/smd` after the M3a bridge subsystem closed
(session 51, 2026-05-11) and the i18n/error-code revision shipped
(session 51 continuation, 2026-05-12). The bridge-subsystem wiring
landed since the previous review and warranted a second look.

## Headline verdict

The lifecycle scaffolding in `run()` is sound — `defer`-ordered
cleanup, panic recovery with a distinct exit code, worker drain
before DB close, hub close after publishers stop. The startup
self-heal for the default logbook (`ensureDefaultLogbook`) is
careful and well-tested. The bridge integration introduced a
regression that violates `run()`'s own anti-pattern note, and two
doc-comment blocks were structurally damaged in a prior refactor.

Counts: **0 Critical**, **3 Major**, **4 Medium**, **5 Minor**.

## Major findings

### M1. `os.Exit(1)` in bridge init/start bypasses every deferred cleanup

**File:** `cmd/smd/main.go:321-328`

```go
bridgeSvc := bridge.New(cfg.Bridge, loggerSvc)
if err := bridgeSvc.Initialize(); err != nil {
    loggerSvc.ErrorWith().Err(err).Msg("bridge: Initialize failed")
    os.Exit(1)
}
if err := bridgeSvc.Start(workerCtx); err != nil {
    loggerSvc.ErrorWith().Err(err).Msg("bridge: Start failed")
    os.Exit(1)
}
```

This is the exact anti-pattern that `run()`'s own preamble
(`main.go:78-81`) cites as the reason `run()` exists:

> The alternative — ad-hoc fatal() calls peppered through startup —
> left open handles when startup failed midway.

By the time control reaches line 321, `dbSvc.Open()` has succeeded
(deferred `Close` registered at 225), `lookupRefresher` is Started
(deferred `Stop` registered at 297), `workerCancel` is registered as
a defer (267), and `spawnForwarderWorkers` has launched goroutines
that are currently writing to the DB. `os.Exit(1)` skips all of
those — leaving forwarder workers writing into an unclosed handle
and an unflushed structured logger.

The Initialize branch is currently dead in practice (the verified
contract of `bridge.Service.Initialize` is "always succeeds if
logger present"), so this matters most for the Start branch.

**Fix:** return wrapped errors, matching every other failure in
`run()`:

```go
if err := bridgeSvc.Initialize(); err != nil {
    return errors.New(op).WithErr(err).WithMsg("initialize bridge")
}
if err := bridgeSvc.Start(workerCtx); err != nil {
    return errors.New(op).WithErr(err).WithMsg("start bridge")
}
```

If a `defer bridgeSvc.Stop()` is added at the same point (mirroring
the refresher pattern at 297-302), the explicit `Stop` call at line
363 stays in the happy-path shutdown sequence and the defer covers
the error-return path.

### M2. Doc-comments above `ensureDefaultLogbook` and `spawnForwarderWorkers` are structurally damaged

**Files:** `cmd/smd/main.go:402-444` and `cmd/smd/main.go:517-520`

Two related defects, almost certainly from a single bad merge:

**(a)** The doc block at 402-444 begins by describing
`spawnForwarderWorkers` ("spawnForwarderWorkers constructs one
worker per enabled forwarder in cfg…") and continues across several
paragraphs, then mid-paragraph at line 422 silently switches subject
into a description of `ensureDefaultLogbook` ("ensureDefaultLogbook
guarantees the row at cfg.DefaultLogbookID exists in the logbook
table at startup…"). The whole 42-line block is attached to
`func ensureDefaultLogbook` at line 445. A reader following Go
convention will assume the entire comment describes
`ensureDefaultLogbook`, including the spawn-site enforcement
invariant in the first half — which doesn't apply to that function
at all.

**(b)** Immediately above the real `spawnForwarderWorkers` at line
521, the doc fragment is:

```go
// loader validates Name uniqueness across cfg.Forwarders before we
// see it). ClaimPendingUploadsWithContext's documentation calls this
// out — don't add a second spawn site without preserving that chain,
// or two workers will share the same destination's queue slice.
```

This starts mid-sentence ("loader validates…") with an unmatched
closing paren on line 1, and is clearly the severed tail of the
original `spawnForwarderWorkers` doc that ended up glued to the wrong
function in 402-444.

**Fix:** split the 402-444 block at the `spawnForwarderWorkers →
ensureDefaultLogbook` boundary; restore the severed opening sentence
of the spawn-site fragment; attach each block to the function it
describes. The load-bearing content ("at most one worker per
forwarder_name", `ClaimPendingUploadsWithContext`'s queue-slice
invariant, the ensureDefaultLogbook three-branch decision tree) is
all still in the file — it's just attached to the wrong functions.

### M3. `doc.go` is two architectural decisions out of date

**File:** `cmd/smd/doc.go:5-10`

```
// smd owns the local SQLite QSO database and forwards logged QSOs to
// configured online services. It exposes an HTTP API over a Unix domain
// socket; clients (Wails desktop apps, wsjtx-bridge, importer-style CLIs)
// submit QSOs and query state through that API.
//
// Scope is deliberately narrow: log + forward, nothing else. Rig control,
// CAT, PTT, audio, FT8 protocol decoding, and capture UX all live in
// separate client or bridge processes that talk to smd over HTTP.
```

Three claims no longer match reality:

1. **"Unix domain socket"** — `cfg.Protocol` supports `tcp`; the
   default deployment serves the embedded SPA over TCP (`ServeSPA=true`,
   per ADR 0001).
2. **"Wails desktop apps, wsjtx-bridge, importer-style CLIs"** — per
   ADR 0001 the only client is the Svelte SPA embedded in the daemon
   binary. Wails was retired; wsjtx-bridge is not in v2.
3. **"log + forward, nothing else… rig control… live in separate
   client or bridge processes"** — per ADR 0013 the bridge runs as an
   in-process daemon subsystem (`internal/bridge`) in the default
   deployment. `cmd/smd` also hosts the enrichment orchestrator,
   refresher, and mailer, which the doc doesn't mention.

**Fix:** rewrite the package doc against ADR 0001 + ADR 0013, point
to `docs/v2-design/structure.md` for the deployment-shape detail
(which is current), and mention the bridge subsystem and enrichment
pipeline so the reader gets an accurate inventory of what runs in
this process.

## Medium findings

### Med1. Deferred close callbacks assign to outer `err`

**File:** `cmd/smd/main.go:159-164`, `cmd/smd/main.go:225-229`

```go
defer func() {
    loggerSvc.InfoWith().Msg("smd stopped")
    if err = loggerSvc.Close(); err != nil {
        _, _ = fmt.Fprintf(os.Stderr, "smd: logger close error: %v\n", err)
    }
}()
```

The deferred callbacks at 161 and 226 both assign to the outer
`err` (note `err =`, not `err :=`). `run()` returns `runErr`, not
`err`, so the return value is unaffected today — but it leaves
`err` mutated at function exit and creates a footgun if anyone
later changes the return to `err`. The correct pattern is already
used at 298 (`if err := lookupRefresher.Stop(); err != nil`); apply
it consistently.

### Med2. `enrichOrchestrator` and `refresher` are hand-wired outside the DI container

**File:** `cmd/smd/main.go:675-694`

Every other long-lived service in `run()` goes through `iocdi`:
config, events, logging, sqlite, qsoservice. The orchestrator and
refresher are constructed directly via struct literal. No harm today
(neither has DI dependents), but searches for "which services exist?"
that grep for `container.Register` will miss these two. Either
register them or add a brief comment at 622 noting that ADR 0017's
provider pipeline is intentionally hand-wired (operator-config
decides which providers to instantiate, which the DI container can't
express).

---

### Med3. Asymmetric service lifecycle treatment across subsystems

CLAUDE.md states the canonical service lifecycle is
`Initialize() → Open()/Start(ctx) → Close()/Stop()`. In `run()`:

| Subsystem | Initialize | Start/Open | Close/Stop |
|-----------|-----------:|-----------:|-----------:|
| DB (sqlite) | via container.Build | manual `Open` (219) | defer `Close` (225) |
| Forwarders | constructed in `worker.New` | `Run` via `safego.GoTracked` | ctx cancel + WG drain |
| Bridge | manual (321) | manual (325) | manual (363) |
| Refresher | manual (679) | manual (682) | defer (297) |
| Mailer | none | none | none |
| Hub | constructed inline | none | manual (397) |

Six different lifecycle shapes for six subsystems. Mailer's "no
lifecycle" is fine (verified: `email.New` has no `Initialize`, and
`Enabled()` keys off `cfg.Smtp.Host`) — but consider documenting in
`run()` why each subsystem diverges from the canonical shape.

### Med4. Mutable package globals reassigned at run() start, never restored

**File:** `cmd/smd/main.go:97-98`, `cmd/smd/main.go:139-144`

```go
qrz.UserAgent = "station-manager/" + Version
adif.ProgramVersion = Version
// ...
iocdi.SetLiteralProvider(func(id string, targetType reflect.Type) (any, bool, error) { ... })
```

`SetLiteralProvider` (verified: package-level `atomic.Value`) and the
two version globals are all writes to package state that persist for
the process lifetime. Fine for a single-shot daemon binary, latent
hazard if any future test imports `cmd/smd` (e.g. an end-to-end test
exercising `run()`). At minimum, a `// global; intentionally
process-lifetime` comment beside each write would mark them as
deliberate.

## Minor findings

### Min1. `resolveConfigPath` duplicates `loadConfig`'s precedence ladder

**File:** `cmd/smd/main.go:703-715` vs `cmd/smd/main.go:722-749`

Both implement the same `explicit flag → SM_WORKING_DIR → cwd`
precedence. If one changes (e.g. adding `XDG_CONFIG_HOME`), the
other will drift. Extract a shared `defaultConfigPath()` helper.

### Min2. Double `workerCancel` is load-bearing but reads as redundant

**File:** `cmd/smd/main.go:267` (defer) and `cmd/smd/main.go:357` (explicit)

Both are needed: the defer covers the error-return path between 267
and 357; the explicit call covers the happy-path shutdown ordering
(needs to run before `server.Shutdown` and the WG drain, not after
function return). A one-line comment on the defer would save the
next reader from suspecting redundancy.

### Min3. `loadConfig` return tuple uses empty-string as a flag

**File:** `cmd/smd/main.go:722`

`(Config, string, error)` where the string means "the path we just
seeded, or empty if we loaded an existing file." Works, but a named
return (`firstRunPath string`) or a small `loadResult` struct would
make the call site at `main.go:101` self-documenting.

### Min4. `hub.Close()` has no timeout

**File:** `cmd/smd/main.go:397`

The drain-wait above (379-391) bounds worker drain via
`ctx.Done()`; `hub.Close()` has no equivalent. If an SSE subscriber
goroutine wedged inside its iteration, shutdown would block
indefinitely. Cheap fix: wrap in the same `select { case <-done:
case <-ctx.Done(): }` pattern.

### Min5. `ShutdownTimeoutSec=0` would silently break drain reporting

**File:** `cmd/smd/main.go:367`

```go
shutdownTimeout := time.Duration(cfg.Server.ShutdownTimeoutSec) * time.Second
ctx, cancel := context.WithTimeout(context.Background(), shutdownTimeout)
```

Verified that `config.applyDefaults` sets `ShutdownTimeoutSec=10`,
so this won't trigger in practice — but if config ever lands with
the field at zero, `ctx.Done()` fires immediately and the drain-wait
select at 384-391 spam-logs "workers did not drain within shutdown
timeout" on every clean shutdown. A defensive `if shutdownTimeout
<= 0 { shutdownTimeout = 10 * time.Second }` would close that gap.

## What's working well

- **`run()` lifecycle scaffolding** (82-399). `defer`-ordered cleanup,
  LIFO ordering deliberately documented at 159 (logger close last so
  later defers can still use the logger), panic recovery in `main()`
  at 62-68 with distinct exit code `ExitPanic=2`.
- **`ensureDefaultLogbook` self-heal** (445-515). Real failure mode
  (operator nukes dev DB without clearing `setup_complete`), three-
  branch decision tree handles every state, corrected-ID persistence
  is non-fatal on write failure (right call — daemon still comes up).
- **Worker drain before DB close** (357-391). Bounded by shutdown
  timeout so a stuck worker can't wedge shutdown indefinitely.
- **Orphan-sweep with bounded context** (253-261). Right pattern for
  a one-shot startup task; doesn't borrow `workerCtx` and won't
  starve under cancellation.
- **`safego.GoTracked` integration** in `spawnForwarderWorkers`
  (587-589). Verified that `respawn=true` actually loops on
  recovered panics until ctx cancellation, and that wg.Add/Done
  lifecycle is handled inside `GoTracked` not at the call site.
- **Test coverage** (`main_test.go`). Real `*sqlite.Service` over
  `:memory:` matches the integration-tests-default rule. Covers
  spawn happy-path / disabled / unknown-type / missing-default-retry
  / explicit-retry-override / invalid-worker-config / empty-list,
  the full self-heal matrix for `ensureDefaultLogbook` (seeds-when-
  missing, no-op-when-exists, no-op-when-setup-incomplete, no-op-
  when-callsign-empty, persists-corrected-ID, warns-when-invalid),
  and the `loadConfig` precedence matrix
  (explicit / env / cwd / first-run-in-cwd / first-run-in-env-dir).
