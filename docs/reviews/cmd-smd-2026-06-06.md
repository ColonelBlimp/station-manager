## Findings

### M1 - Default config resolution can silently fall back to cwd when the configured working directory fails

`defaultConfigPath` swallows `utils.WorkingDir()` failures and returns `cwd/config.json` instead:

- `cmd/smd/main.go:871-876`
- `internal/utils/working_dir.go:33-55`

That matters because `utils.WorkingDir()` is the resolver for an explicit `SM_WORKING_DIR`, the XDG data-dir fallback for packaged installs, and directory creation. If `SM_WORKING_DIR` is set but inaccessible, or the XDG data directory cannot be created, the daemon should fail loudly. Today it can instead read or seed `config.json` in the process cwd.

The risk is starting the daemon with the wrong config and data directory after an operator intended a specific working directory. In a systemd deployment that can mean the service comes up on defaults while the real config is merely inaccessible. This is especially risky because `loadConfig` also treats every non-nil `os.Stat(candidate)` result as "config missing" and enters first-run write:

- `cmd/smd/main.go:909-914`

Recommendation:

- Make config-path resolution return `(path string, err error)`.
- Propagate `utils.WorkingDir()` errors instead of falling back to cwd.
- In `loadConfig`, only enter the first-run path for `os.IsNotExist(statErr)`. Return other stat errors.
- Add tests for "working dir resolver fails" and "default config path stat returns non-not-exist error". The latter can use a small injectable stat helper or a chmod-based test guarded for platforms/users where permissions behave predictably.

### M2 - Default logbook self-heal does not keep the corrected ID in memory when config persistence fails

`ensureDefaultLogbook` inserts a missing default logbook and, when the inserted ID differs from `cfg.DefaultLogbookID`, tries to persist the corrected ID through `cfgSvc.Update`:

- `cmd/smd/main.go:615-630`

The comment and warning say the daemon still comes up with the corrected ID in memory if writing `config.json` fails. That is not what `config.Service.Update` does. `Update` writes the file first and only assigns `s.Cfg = next` after `WriteJSON` succeeds:

- `internal/config/config.go:1073-1101`

Trigger:

1. `config.json` has `setup_complete=true` and `default_logbook_id=42`.
2. The DB was recreated, so the logbook row is missing.
3. Startup inserts a new default logbook, likely ID `1`.
4. `config.json` cannot be rewritten.

Current result: `ensureDefaultLogbook` logs that the ID was corrected in memory, returns nil, `run` snapshots `cfgSvc` at `cmd/smd/main.go:327`, and the server continues with stale `DefaultLogbookID=42`. The first QSO submit can still hit the exact missing-logbook/FK failure this self-heal path was meant to prevent.

Existing tests cover successful correction (`cmd/smd/main_test.go:618-643`) but not the write-failure branch.

Recommendation:

- Either make this branch truly update the in-memory config even when persistence fails, or return an error instead of starting with a stale ID.
- If the intended policy remains "persist failure is non-fatal", add a config-service method for session-only mutation or a two-step update that can commit memory and separately report disk persistence failure.
- Add `TestEnsureDefaultLogbook_PersistFailureKeepsCorrectedIDInMemory`, using an unwritable or invalid `cfgSvc.Path` so `WriteJSON` fails deterministically.

### L1 - User-Agent is not normalized before being persisted and passed to QRZ forwarding

`run` uses `strings.TrimSpace(cfg.UserAgent)` only to decide whether to synthesize the default, but it does not assign the trimmed value back:

- `cmd/smd/main.go:156-188`

That means `" station-manager/dev "` is accepted, persisted as-is, and assigned to the QRZ forwarder package global. The forwarder then sends the raw value as the HTTP header:

- `internal/forwarding/qrz/qrz.go:78-85`
- `internal/forwarding/qrz/qrz.go:215-216`

Hamnut and QRZ lookup services trim their own `UserAgent`, so this is mostly a forwarding/config hygiene issue. Still, outbound HTTP headers should use the same canonical global value everywhere.

Recommendation:

- Set `cfg.UserAgent = strings.TrimSpace(cfg.UserAgent)` before the defaulting branch.
- Consider validating maximum length in the global config path if the QRZ forwarder requirement of <=128 chars is meant to be a daemon-wide invariant.
- Add a narrow test around a helper such as `resolveUserAgent(cfg.UserAgent, Version)`.

### L2 - Package docs and shutdown comments have drifted from the current daemon shape

The runtime behavior is broadly sound, but some documentation now points reviewers in the wrong direction:

- `cmd/smd/doc.go:3-7` lists database, forwarding, enrichment, SMTP, and bridge, but omits the FT8 subsystem that `run` now constructs at `cmd/smd/main.go:429-448`.
- `cmd/smd/doc.go:16-20` names the old `internal/storage` and `internal/forwarder` packages; the current names are `internal/database/sqlite` and `internal/forwarding`.
- The bridge comment says it is "stopped after server.Shutdown" (`cmd/smd/main.go:398-405`), but the actual ordered teardown stops bridge before HTTP shutdown (`cmd/smd/main.go:477-484`, `cmd/smd/main.go:508-510`).
- The bridge shutdown comment says Stop closes "the hub" (`cmd/smd/main.go:479-482`). That is the bridge subsystem hub, not the daemon `events.Hub`, which is closed later at `cmd/smd/main.go:530-540`.

Recommendation:

- Update `doc.go` to include FT8 and current package names.
- Adjust the bridge shutdown comment to match the current order and distinguish the bridge hub from the daemon event hub.

## Notes

- `run` is still intentionally process-shaped: it uses the process-global `flag.CommandLine`, `signal.Notify`, package globals (`adif.ProgramVersion`, `qrz.UserAgent`, `iocdi.SetLiteralProvider`), and `os.Args` dispatch in `main`. That is acceptable for the single-shot daemon binary, but it keeps full `run()` integration testing awkward. If more daemon-level tests are added, consider factoring pure helpers for flag parsing, User-Agent resolution, and shutdown wiring instead of calling `run` repeatedly.
- `runImport` is well scoped. It uses a fresh `FlagSet`, parses and dry-runs ADIF before touching config/DB, reuses the canonical QSO import path, and has tests for happy path, dry-run, idempotency, Station Manager field preservation, and QRZ LOGID stamping.
- Lifecycle ordering is materially better than the older review baseline. Workers are cancelled before server shutdown and DB close; bridge/FT8 have explicit Stop calls plus deferred error-path cleanup; lookup refresher Stop is deferred while DB remains open; the daemon event hub closes after publishers and HTTP handlers have drained.
